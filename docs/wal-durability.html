when you click Save?

Your app says “saved.” Then the computer loses power. Will your data still be there?

That question connects everything in this guide: databases, memory, write-ahead logs, disk synchronization, and BQL. We’ll follow one small change from your screen to a second computer, learning each idea when we need it.

01 / The job of a database

Keep facts, and change them safely.

A database is an organized collection of information. Your to-do app might store a table: one row for each task, with a title and a “done” field. The database software knows how to find, change, and save those rows.

Let’s mark “Buy milk” as done. The app sends an instruction, often written in SQL, a language for working with databases:

UPDATE tasks SET done = true WHERE id = 7;
BeforeTask 7: Buy milk · unfinished
→
AfterTask 7: Buy milk · done

Sometimes a change needs several steps. A money transfer, for example, subtracts from one account and adds to another. A transaction groups changes so they take effect together. You don’t want half a transfer.

Commit means accepting that transaction. Rollback means abandoning it. There is still another question: has the accepted change reached storage that survives a power failure?

Two promises to keep separate

“The whole change took effect” is about atomicity. “The accepted change survives a crash” is about durability.

02 / Why saving is more than writing

A computer has a workbench and a filing cabinet.

That’s a useful analogy for RAM and persistent storage. RAM is fast working memory. An SSD or disk is where data can remain after power is off.

RAM / WORKING MEMORY

Fast, temporary workspace

Applications use RAM while running. The operating system also uses RAM to hold recently written file data. This holding area is called the page cache.

Ordinary RAM loses its contents when power disappears.

SSD OR DISK / PERSISTENT STORAGE

Data that can survive a restart

Once data is durably stored, turning the computer off should not erase it. Reaching that point takes work by the operating system and storage device.

A broken or destroyed drive is a separate problem.

When a program writes a file, the operating system may first put those bytes in its cache and report success. It can write them to storage later, combining work for efficiency.

So “the write returned” does not automatically mean “the data is on durable storage.” An app crash may leave the operating system’s cache intact. A power failure takes that cache away.

03 / How SQLite changes a database

Write the new pages beside the old ones.

SQLite is database software an application can run directly, without a separate database server. It stores information in files. Internally, a database file is divided into fixed-size chunks called pages.

A page is a chunk of bytes, not a screen or a single row. Changing one task can affect several pages. To keep our example small, imagine it changes pages 2 and 5.

In write-ahead log (WAL) mode, SQLite first writes new page versions into a separate file. The main database can keep its old pages for now. “Write ahead” means writing the changes to the log before folding them into the main file.

Each page entry in the WAL is called a frame. The last frame of a committed transaction marks its boundary. Incomplete work is not exposed as a completed transaction.

SQLite’s WAL allows readers alongside a writer, but each database still has only one writer at a time. SQLite: write-ahead logging.

04 / Crossing the durability boundary

fsync means “wait for this file to be synchronized.”

fsync is a request to the operating system: flush this file’s pending data and required metadata to storage, and report when that completes. Metadata is information about a file, such as its size.

Think of an ordinary write as handing a document to a filing clerk. fsync is waiting for confirmation that the filing work is complete.

write()Submit the bytes

The application hands file data to the operating system.

→
OS CACHE / RAMThe write can return here

Bytes may still be waiting in memory. Power loss can lose them.

→
fsync() completesStorage confirms the flush

The caller has waited for the requested persistence barrier.

This relies on the operating system, filesystem, and storage device honoring the synchronization request.

Waiting for storage takes time. A system can wait on each transaction for a stronger promise, or group and delay flushes for less waiting. The second choice can leave a window where recent changes are vulnerable.

A checkpoint and an fsync do different jobs. A checkpoint moves page versions into the main database. An fsync makes pending file writes durable. Your new data can be durable in the WAL before it reaches the main database file.

Another name you’ll see in BQL: fdatasync

fdatasync flushes file data and the metadata needed to retrieve it. Where the platform permits, it can omit unrelated metadata updates. BQL synchronizes its transaction log with fsync and SQLite’s WAL with fdatasync.

Does fsync protect against every failure?

No. It does not create a copy on another machine or protect a drive from physical destruction. It also does not make unrelated updates to several files atomic. Creating or renaming files can require synchronizing the containing directory as well.

05 / What BQL adds

Turn local changes into a history other machines can follow.

BQL is a database system built around SQLite. It can run inside your application or serve requests over a network. It uses Bun, a runtime that executes JavaScript and TypeScript programs.

SQLite’s WAL solves local database problems, but it is reused. BQL needs a history it can keep after that reuse, send to other machines, and upload for backups. So it creates a second log.

After SQLite commits, BQL reads the committed page changes and packages them into a transaction record. BQL compresses the record and appends it to a log file. As the log grows, it uses multiple files called segments.

Why save pages instead of rerunning SQL?

A receiving machine can apply the results directly. It does not need to execute the original “mark task done” instruction again.

Before applying, BQL can check: “Am I at transaction 41? Does my current state match what record 42 expects?” A mismatch should trigger recovery rather than quietly building on the wrong data.

Keeping this extra history costs disk space, compression work, and additional writes. It pays for capabilities we’ll see next.

The rule that connects the two logs

BQL must record committed changes before checkpointing can discard the SQLite WAL history needed to reconstruct them.

06 / Surviving beyond one computer

A replica and a backup solve different problems.

The primary is the server accepting writes for a database. A replica is another server holding a copy. A backup is retained data you can restore from later.

BQL’s transaction log

One ordered history, several uses.

↓
Send to a replica

Verify the record, apply its pages, and synchronize the result. The replica can serve reads and may become a new primary.

Upload for backup

Send records and periodic full copies, called snapshots, to an S3-compatible bucket: a remote service for storing files as objects.

Replay after a failure

Use the surviving records to rebuild the database state they describe.

A replica helps when a server fails. But if you accidentally delete every task, that valid deletion can reach the replica too. Retained backup history lets you restore to before the mistake.

BQL restores by starting with a snapshot and applying later transaction records in order. A point-in-time restore means choosing how far along that history to go.

Copies can lag behind.

BQL uploads to S3 in the background. A successful write does not mean the backup already contains it. Restoring depends on what was uploaded and retained.

How does a replica take over without two servers both writing?

In cluster mode, BQL uses a coordination protocol called Raft to agree on control information, including which server may write each database. That permission is a time-limited lease. A server must stop accepting writes when its permission expires.

A new leadership version, or epoch, helps reject an outdated writer. Each SQL write checks its existing permission locally; it does not run through Raft individually. This coordination is separate from waiting for copies of the data.

07 / Choose what “saved” promises

The app can wait for different levels of safety.

An acknowledgment, shortened to ack, is the server’s success response. BQL lets the caller choose what must happen before that response. More waiting can confirm that more copies are safe, but it also increases response time and dependence on other machines.

1. CommitAccept the local change.
2. Local diskSynchronize the log and WAL.
3. Other machinesWait for durable replica replies.
S3 backupAlways in the background.

“Saved durably on this machine.”

BQL commits the change, appends its record, synchronizes the BQL log and SQLite WAL, then responds. No second machine needs to confirm.

What you get: protection against losing the change merely because the primary loses power, assuming storage honors synchronization. A destroyed primary disk still requires another copy.

A timeout can mean “written, but not confirmed elsewhere.”

If the primary committed but replica replies arrive too late, BQL reports an acknowledgment timeout. That does not undo the transaction. Repeating a non-idempotent action, such as incrementing a balance, could apply it twice.

A detail for later: quorum and the low-level API

Here, quorum means a majority of the primary plus currently attached replica nodes, with local synchronization required. With a primary and two attached replicas, the primary plus one replica is enough. This is separate from Raft’s voting membership.

The server implements the remote waits. The low-level Tenant.write() method alone treats replica and quorum levels as local fsync durability; it does not itself wait for replica replies.

08 / When a crash interrupts the steps

Find the last state the surviving data can prove.

The database, its WAL, BQL’s log, and the saved progress marker are separate pieces. A crash can interrupt work between updating them. On restart, BQL compares them and reconciles recoverable differences.

THE WAL HAS MORE

Rebuild the missing history

If SQLite committed changes that BQL did not finish recording, surviving committed WAL pages can be used to reconstruct the missing log records.

THE LOG HAS MORE

Bring the database forward

If BQL’s surviving log contains changes the database needs, replay those verified records into the database.

THE LAST RECORD IS PARTIAL

Discard the incomplete tail

If a crash interrupted a log append, trim the unfinished end to the last valid record, then reconcile the remaining data.

Checksums and sequence numbers help detect damage and missing steps. They cannot recreate bytes that disappeared from every copy. That is why synchronization, replicas, and backups matter before a failure happens.

09 / Where BQL earns its extra machinery

Better for a particular job.

BQL’s strongest argument is bringing several jobs together around SQLite: serving requests, managing separate customer databases, streaming changes to replicas, waiting for durable copies, and maintaining backups.

Imagine a to-do service used by 500 companies. Each company can have its own SQLite database. This is called multi-tenancy: one service hosts data for many customers. BQL manages those databases in a common system, rather than requiring you to assemble all of those surrounding pieces yourself.

Separate customer data

A database per customer gives each customer its own data boundary, write history, and restore target. It does not automatically isolate all CPU or memory usage.

One history powers several features

The same transaction records support replication, backup, and recovery. This gives those features a common way to describe progress and verify state.

Choose the promise per write

The API can wait for local synchronization or replica confirmations. You can match the response promise to the importance of the operation.

BQL does not remove SQLite’s one-writer-per-database limit. Splitting customers into separate databases spreads independent work, but it does not make one very busy database accept unlimited concurrent writers.

The extra log also means extra storage and processing. Waiting for a replica adds network delay. Backups require monitoring and restore practice. Those costs are worthwhile when you need the features they support.

There is no evidence here that BQL is universally faster, safer, or cheaper than the alternatives. Its architectural fit is the case for considering it. A production decision also needs workload benchmarks, failure tests, and operational experience.

The reason to choose BQL

You want SQLite’s local database model plus an integrated way to serve, replicate, back up, and manage many databases—and those benefits justify the additional system you will operate.

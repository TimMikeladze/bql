# The bus on a bql.sh database

Status: built. This is step 3 of "The work after this" in `docs/monorepo.md`, decided here
rather than arrived at. What landed in each step is under "Built", "Step 4 built", "Step 5
built" and "Step 6 built" below; the sections before them are the plan as written.

The bus keeps its state in one SQLite file it opens through `bun:sqlite`, replicates its own log
over HTTP (`src/bus/replication.ts`), fails over by hand through a lease file, and backs up with
its own `backup` / `restore` commands. bql.sh already does each of those for SQLite databases:
WAL shipping, `ack: "replica"` / `"quorum"`, a Raft control plane with epoch-fenced automatic
promotion, S3 shipping and point-in-time restore. This moves the bus's state into one bql.sh
database, named `bus`, and deletes the bus's own versions.

## What it buys

| | bus today | bus on bql.sh |
|---|---|---|
| Replication | log rows + cursors over HTTP, async | WAL shipping: every table, including deliveries and leases |
| Publish durability | local commit | `ack: "fsync" / "replica" / "quorum"` |
| Failover | `bql bus promote --lease`, by hand | Raft lease lapses, a replica is promoted automatically |
| Fencing | lease file polled every 5 s | epoch on every record; a stale primary's records are rejected |
| In-flight work after failover | leases lost, deliveries rebuilt from cursors | leases and generations survive; a consumer's ack still lands |
| Backup | `bql bus backup` / `restore` | bql.sh S3 shipping and `bql restore --at` |
| Write scale-out | none | still none: one primary for database `bus` |

## Where the bus runs

**In the bql.sh server process.** The bus's single-writer guarantees, Tier 1 transactional acks
and the conditional `UPDATE` on claim all depend on synchronous transactions against a local
file. Running the bus as a client of bql.sh over HTTP would turn each of those into a round trip
and lose Tier 1 entirely. So:

```sh
bql serve --cluster … --bus           # every node mounts the bus routes under /bus
```

```toml
# bql.toml
[bus]
enabled = true
database = "bus"        # the bql.sh database holding the bus tables
ack = "replica"         # publish durability; any ack level bql.sh supports
```

Every node mounts `/bus/api/*`. The node holding the primary of database `bus` runs the bus
store as writer: publish, claim, ack, the sweep and the scheduler. Every other node opens the
store read-only and answers writes with `503 NOT_PRIMARY` plus a `BQL-Primary` header, the same
redirect the database routes use. `BusClient` takes a list of URLs and follows the header. A
consumer pointed at any node therefore ends up leasing from the primary.

`bql bus serve` stays as a single-node shortcut: it runs `Bql.open` on its `--data` directory
with one database and no cluster, so a laptop setup is still one command.

## The pieces

### Driver swap (monorepo step 1)

`src/bus/store.ts` imports `Database` from `bql.sh/sqlite` instead of `bun:sqlite`. The shape was
kept deliberately compatible (`open`, `exec`, `prepare`, `query`, `run`, `transaction`). It is
useful alone (statement deadlines, a real `walCheckpoint` result) and it shows which `bun:sqlite`
behaviours the store relied on before the larger change. Ships on its own; bus tests must pass
unchanged.

### Blobs in the database

Bodies over `inlineMaxBytes` (64 KiB) go to files through `FsBlobStore`. WAL shipping only
carries the database, so a replica would have the row and not the bytes. A `SqliteBlobStore`
implements the existing `BlobStore` seam with a `blobs_data(handle TEXT PRIMARY KEY, bytes BLOB)`
table in the same database. `body_sha256` and `body_bytes` are still checked on read. This
changes write amplification for large bodies; the bench below measures it.

### The store on a tenant

The store stops owning a connection. It gets the embedded `Db` for database `bus` and runs every
write through `db.sync.transaction(…)`, so each one goes through the tenant's write path and comes
out as a `TxnRecord`. Reads use `db.sync.sql`. Of the 23 `transaction(` call sites in
`store.ts`, all already run synchronous bodies, which is what `sync.transaction` takes.

Two additions to bql.sh are needed:

- `sync.transaction` returns the committed `txid` alongside its value
  (`{ value, txid }`, or an `EmbeddedCommit` already defined in `embedded.ts`).
- `await bq.replicated(db, txid, { ack })` resolves once the chosen ack level covers `txid`, and
  throws `ACK_TIMEOUT` / `NO_REPLICAS` exactly as the HTTP path does. A publish commits
  synchronously, then awaits this before answering. A synchronous body cannot wait on a network
  ack, so the wait has to sit outside the transaction.

### Role changes

`ServerRuntime.roleChanged(db, role)` already fires from `Promoter.#flip`. The bus listens for
its own database:

- becoming primary: open the store as writer, start the sweep and the scheduler, reload
  in-memory caches (schema bindings, quotas).
- becoming replica: stop the sweep and the scheduler, drop to read-only, fail in-flight long
  polls with `503 NOT_PRIMARY`.

Expired leases on the new primary are reclaimed by the ordinary sweep, the same as after a
restart. Leases that have not expired stay with their consumer, whose next renew or ack arrives
at the new primary with the same `generation`.

### Realtime

The dashboard and `/api/stream` poll today. Database `bus` has bql.sh's commit hooks, so the SSE
stream can be driven by them. Not required for this spec; listed because it becomes free.

## What gets deleted

- `src/bus/replication.ts`: `fileLease`, `follow`, `promote`, `fenceWatcher`.
- The `cluster` table, `store.demote` / `store.promote`, `applyReplicated`, `applyCursors`,
  `applySchedules`.
- CLI `follow`, `promote`, `backup`, `restore`. `bql bus restore` points at `bql restore` for one
  release, then goes.
- `scripts/failover-drill.ts` is rewritten against a three-node bql.sh cluster; it must report
  zero acknowledged publishes lost under `ack = "replica"`.

## Migrating an existing bus

`bql bus migrate --from ./old-data --into ./bql-data` checkpoints the old file with `TRUNCATE`,
copies it in as database `bus`, moves file blobs into `blobs_data`, and drops the `cluster`
table. The old directory is left untouched. Before this is written I want to confirm the registry
adopts a pre-existing `main.db` with no log: as far as I can tell it should take it as txid 0, but
I haven't tested it.

## Risks I want measured before committing to it

- **Per-statement overhead.** The embedded path does more per statement than a cached
  `bun:sqlite` prepared statement. The bus runs several statements per claim. Baseline: current
  soak and publish/claim/ack throughput on `bun:sqlite`; the change must not regress them by more
  than an agreed margin. Interleave A-B-A-B runs; the bench machine is never quiet.
- **WAL volume.** Every claim, renew and ack is a write, so a busy consumer fleet produces a
  `TxnRecord` per lease renewal. Measure log bytes per delivered message and replica lag under
  the soak.
- **Bodies in the database.** 1 MiB bodies now go through the WAL and the log. Measure against
  file blobs.
- **One database.** Workspaces stay as a column. Splitting each workspace into its own bql.sh
  database would spread primaries across nodes and give some write scale-out, but `seq` is
  global today and cross-workspace admin queries assume one file. Out of scope here.

## Order

1. Driver swap. Independent, ships alone.
2. `SqliteBlobStore`. Independent, opt-in behind a flag at first.
3. The two bql.sh additions (`txid` from `sync.transaction`, `bq.replicated`).
4. Store on a tenant, single node (`bql bus serve` on `Bql.open`). Full bus suite and the soak
   pass; bench compared.
5. Cluster mode: `--bus` on `bql serve`, role changes, `NOT_PRIMARY` redirect, `BusClient` URL lists.
   New failover drill.
6. Deletions and `bql bus migrate`.

Steps 1 to 4 leave today's replication working. Step 5 is where the two coexist for one
release; step 6 removes the old path.

## What this replaces

An S3 conditional-put lease and a follower ack protocol for the standalone bus were considered on
2026-10-21 and dropped: both fix the bus's own replication, which this spec deletes.

## Binding the store to a tenant (findings)

Step 3 landed in `packages/db/src/embedded.ts`. `db.sync.commit(fn, { ack })` is
`sync.transaction` returning `{ value, txid }`; a transaction that wrote nothing answers the
current txid, the same rule `Tenant.txCommit` follows. `ack` sets what the commit does locally
(`"local"` or an fsync) and pre-checks `"replica"` / `"quorum"`, refusing with `NO_REPLICAS` before
`BEGIN`. `await bq.replicated(db, txid, { ack })` does the waiting through the runtime's existing
`AckTracker` (`awaitDurable`), so `ACK_TIMEOUT` carries `txid`, `acks` and `needed`, and
`ackTimeoutMs` and per-database `ackWithoutReplicas` apply exactly as on the HTTP path.
`bq.assertReplicas(db, ack)` is the pre-check on its own. `BqlClientError` now carries `acks` and
`needed`, which it used to drop for HTTP clients too.

The store can run on the `sync` surface, but not unchanged. `sync.transaction` does not nest: a
second one, or a `sync.sql` write, while one is open throws `TX_BUSY`, so the nested
`db.transaction` calls in `store.ts` have to be flattened or passed the outer `tx`. Inside the
callback `tx.sql` runs on the writer and sees its own writes, but `db.sync.sql` goes to a pooled
reader and does not, so every helper the store calls from inside a transaction has to take the
`tx` rather than read through `this.db`. Pragmas, probed as admin: `wal_checkpoint(TRUNCATE)` fails
with `BUSY` (it runs inside the writer's transaction), `journal_mode = delete` fails, `ATTACH` fails
(`max 0` attached databases), and `VACUUM` fails. `wal_autocheckpoint`, `synchronous`,
`busy_timeout` and `foreign_keys = on` all "succeed", but SQLite calls them read-only, so they run on
whichever pooled reader was borrowed and change nothing on the writer. A bare `begin` does the same
and leaves that reader inside an open transaction, which is a bql.sh bug worth fixing separately.
The store should drop all of its pragmas: the tenant checkpoints on its own (`checkpointWalBytes`),
`bq.checkpoint("bus", "TRUNCATE")` replaces the sweep's `wal_checkpoint`, durability is the ack
level (the bus defaults to `synchronous=FULL` today, which is `ack: "fsync"`), and `foreign_keys`
is the per-database setting (`PATCH /v1/db/bus`, or `[sqlite] foreignKeys`).

Overhead, measured with a microbench on an 18-core machine at load 10 (interleaved, four rounds,
two runs, medians; writes yield a microtask per op so the deferred log append is paid inside the
timing). A point read by primary key: 1.3 to 1.5 µs on a cached `bun:sqlite` statement, 2.8 µs
through `db.sync.execute`, 0.9 µs through `tenant.readSync((d) => d.query(sql).get(id))`. A
three-statement write transaction at `ack: "local"`: 18 µs on `bun:sqlite`, 43 µs through
`tenant.write` with cached statements, 55 µs through `sync.commit`. Most of the write cost is the
capture (WAL frames to a `TxnRecord`, encode, append), which any binding that replicates pays. The
`sync` surface adds roughly 1.5 µs per read and 4 µs per statement in a transaction on top. I
suspect most of that is `resolveOptions`, the `prepare().readonly` classification and building a
`Result` on every call; I haven't profiled it.

The faster binding is `tenant.write(fn)`, which hands `fn` the writer `Database` from
`bql.sh/sqlite` (the driver step 1 already moved the store to) inside `BEGIN IMMEDIATE`, and
captures the commit into the log. Nested `db.transaction` calls on that handle become SAVEPOINTs,
cached `query()` statements survive, and reads see the transaction's writes, so the store's code
keeps its shape. Calling `tenant.write` directly skips things the runtime does on every write, so
the binding has to put them back: `runtime.assertWritable(db)` first (the Raft lease; without it a
fenced node keeps writing), `runtime.assertAckAvailable`, `runtime.markStatement` after (the realtime
statement boundary), and error mapping. It also has rules the caller must keep: never use the
handle after `fn` returns, never `BEGIN`/`COMMIT`/`ROLLBACK` by hand, no checkpoint, `journal_mode`,
`ATTACH`, or connection pragmas on the writer (the admin principal has no authorizer to stop
them), and expect `BUSY` while a snapshot holds the writer (a replica bootstrapping takes one) and
`TX_BUSY` while an HTTP baton transaction on `bus` is open. I recommend this: add
`db.sync.write(fn: (d: Database) => T, { ack }): SyncCommit<T>` and `db.sync.read(fn)` to
`embedded.ts`, wrapping `tenant.write` / `tenant.readSync` with those checks, and give the store a
two-method port (`write`, `read`) instead of a `Database`. It is a few dozen lines, keeps the
invariants in bql.sh, and spares rewriting 23 transaction sites around `tx`.

Cluster wiring. `Bql.open` builds the whole `ServerRuntime`, including the `ClusterNode` when
`[cluster]` is enabled and the `ReplicationServer` when there is a secret, but starts none of the
background parts. `startServer` starts the Raft node and the promoter (`startCluster`), the
replication client (`startReplication`) and the S3 shipper (`startStorage`) only when it built the
runtime itself. `bq.serve()` hands in its own runtime, so it skips all three and forces one worker.
An embedded primary that serves does accept replicas and count their acks (the tests here do
exactly that), but it never joins Raft, never follows a primary and never ships. Step 5 needs
either `bq.serve()` to start the three when the config asks for them, or a hook in `startServer`
for `bql serve --bus` to build the bus on the runtime it owns. The bus also needs `[server] workers
= 1` on its node, or the `bus` tenant lives on a worker thread instead of beside the store.
`ServerRuntime.roleChanged` was a single slot, taken by the worker entry; it now also fans out to
`runtime.onRoleChange(listener)` listeners, exposed as `bq.on("role", ({ db, role }) => …)`, plus
`bq.role(db)` for the role at startup, which fires no event. A flip evicts and reopens the tenant,
so the store must not cache `db.tenant()` across one; `bq.db("bus")` looks it up per call.

Adopting an existing file. A `main.db` dropped into the tenant directory is not adopted: the
registry is driven by the catalog, so `bq.list()` doesn't show it and queries answer
`DB_NOT_FOUND`. `bq.create("bus")` over that file opens it at txid 0 and writes work, even across a
reopen, but that is an accident: the position's checksum is the empty database's, and nothing
below txid 1 is in the log, so a restore to a txid before the first snapshot cannot rebuild it.
The supported path is `registry.importDatabase(name, bytes)` (`POST /v1/db/{db}/import`): it
switches the file to WAL, folds it with `TRUNCATE`, and starts the row at txid 1 with the file's own
checksum. Tested: the rows are there, `txid` is 1, the next commit is 2. It takes the file as bytes
in memory, so `bql bus migrate` should do its own work on a copy first (checkpoint, move blobs into
`blobs_data`, drop `cluster`) and import the finished file once.

### Built

`db.sync.write(fn, { ack })` and `db.sync.read(fn)` are in `packages/db/src/embedded.ts`.
`write` runs `runtime.assertWritable` and `runtime.assertAckAvailable`, then `tenant.write` with
`fn` given the writer `Database`, and calls `runtime.markStatement` once after `fn` (the callback is
one statement to the change feed). It answers `{ value, txid }`; `ack` behaves as on `sync.commit`.
`read` borrows through `runtime.withReader` as admin. A throw from `fn` comes out unchanged
(a `SqliteError` stays one); everything else is a `BqlClientError`. Contention is not waited for:
`TX_BUSY` while a baton transaction holds the writer, `BUSY` during a snapshot or for a
`sync.write` nested in another. The store should retry those after yielding.

The forbidden statements are refused by a new driver slot, `Database.guard(cb)`, asked about
`TRANSACTION`, `PRAGMA`, `ATTACH` and `DETACH` actions at compile time and again on a statement
cache hit (each `Statement` now records those actions in its program facts). It is not the
authorizer, because switching the authorizer expires every cached statement, which is the cost
`write` exists to avoid. `src/server/guard.ts` switches it on around `fn` and turns a refusal into
`NOT_AUTHORIZED` naming the statement. Allowed pragmas: the token policy's list plus
`defer_foreign_keys`, `foreign_key_check`, `integrity_check`, `quick_check`, `user_version`.

The `begin` leak is fixed in two places: `Tenant.releaseReader` rolls back a connection returned
inside a transaction (or closes it), and `runtime.withReader` answers `BAD_REQUEST` when the
statement left one open, so `sync.execute("begin")` and `POST /query {"sql":"begin"}` are refused.

`bq.serve()` now starts `startCluster`, `startReplication` and `startStorage` after it listens,
the order `startServer` uses for its own runtime, and `bq.close()` awaits `closeStorage` before
closing the runtime, which stops Raft and the replication clients. Embedded serve stays at one
worker. `packages/db/test/embedded/cluster.test.ts` runs three `Bql.open` + `serve()` nodes, closes
the primary of a database, and checks a survivor's `bq.on("role")` fires `"primary"` and its
`sync.write` commits at the next txid.

### Step 4 built

The store runs on either backend behind `src/bus/storage.ts`. A `StorageBackend` has `write(fn,
{ ack, mode })` returning `{ value, txid? }`, `read(fn)`, `assertAck(ack)`, `replicated(txid,
ack)`, `checkpoint(walBytes)`, `sizes()`, `close()`, plus `defaultAck` and `path` (for `statfs`).
`fileStorage(path)` is the old constructor body: it opens the file with `statementCache: 512`,
sets the five pragmas, and `write` is `db.transaction(fn, mode)(db)`. `bqlStorage(bq, { database,
ack })` is `db.sync.write` / `db.sync.read` on database `bus`, looked up per call so a role flip's
reopen is picked up.

The store did not get rewritten around `tx`. It talks to a `StoreDb`, a connection-shaped handle
(`query().get/all`, `run`, `transaction`) that routes each call: inside a write, to the writer
the backend handed out, so a read sees the transaction's own writes and a nested `transaction` is
a SAVEPOINT; outside one, a read goes through `read` (a pooled reader) and a bare `run` becomes a
write of its own. On the file backend, outside a transaction, it goes straight to the one
connection, so a bare `run` is still an autocommit statement. All 23 `transaction(` sites, every
bare `run` (sweep, scheduler, consumer registry, audit, quotas, revocations), the migrations and
`SqliteBlobStore` go through it with no change at the call site. `raw()` returns the handle, so
`raw().run("CREATE TABLE …")` from an embedder is a write too. `ackTransactional` hands the
handler the writer itself (`StoreDb.writer`), which on bql is the guarded writer inside
`sync.write`.

Pragmas: all five moved into `fileStorage`; the bql backend sets none. Checkpointing is a no-op
there (the tenant has `checkpointWalBytes`), and `sizes()` reads the tenant's `sizeBytes` /
`walBytes`, so `bql_bus_db_bytes` and `_wal_bytes` keep working. The bus does rely on foreign
keys (`deliveries` and `blocked_keys` cascade from `messages` and `subscriptions`), so
`ensureBusDatabase(bq)` creates `bus` if missing and `registry.setForeignKeys("bus", true)` unless
the row or `[sqlite] foreignKeys` already has them on. `backup` (`VACUUM INTO`) refuses on bql.

Contention. `sync.write` throws `BUSY` while a snapshot holds the writer and `TX_BUSY` while a
baton transaction does, and a single-node bus still sees the first: the runtime's sweep snapshots
every `snapshotIntervalMs`. I put the waiting in two places rather than making every store method
async. The async methods that carry the traffic (`publish`, `publishBatch`, `claim`, `ack`,
`runSchedule`, the scheduler's fire) run their top-level write through `retryContention`, which
sleeps 1 to 50 ms between tries for up to 5 s; the refusal comes before `fn` runs, so a retry
repeats nothing. Everything else is synchronous and called from a route, so `createServer` reruns
the whole route on `BUSY`/`TX_BUSY` with the same backoff. The body is read once and memoized,
the rate limiter charges only the first attempt, and an `AsyncLocalStorage` counts the commits the
attempt made: a route that committed something before it was refused answers `503 {"code":
"BUSY"}` with `Retry-After: 1` instead of running twice. The CLI's sweep timer skips a contended
tick; `consumeTransactional` and the `DirectClient` wrap their synchronous calls the same way.

Publish durability. `PublishRequest.ack`, a batch-level `ack` on `/api/publish/batch`, and `ack`
on an ack that publishes take bql.sh's `Ack`; `--ack` / `BUS_ACK` is the server default, `fsync`
when unset. The store calls `assertAck` before `prepare` (so a refusal writes no blob and no
row), commits through `sync.write({ ack })`, then `await bq.replicated("bus", txid, { ack })`.
`NO_REPLICAS` and `ACK_TIMEOUT` come back as `503 { error, code, txid, acks, needed }` plus `seq`
(single publish), `results` (batch) or `published` (ack), the field names `api.md` uses. Results
carry `txid` on bql. A replayed ack wrote nothing, so its `txid` is the current one, which covers
the original and is waited on. Plain acks, nacks and renewals commit at `local` under `--ack
local` and `fsync` otherwise, and wait for nothing else. The file backend takes `local` and
`fsync` and answers `replica` / `quorum` with 400 (`--ack replica` without `--storage bql` refuses
to start).

Wiring. `bql bus serve --storage bql` opens `Bql.open({ dir: "<data>/bql" })` and database
`--database` (default `bus`); keys, the admin token and file blobs stay in `<data>/`. It does not
call `bq.serve()`: nothing in step 4 needs the bql.sh HTTP surface, and not serving it means no
baton transaction can hold `bus`. `createBus({ bql, database, ack })` takes an engine the caller
opened (and closes only the bus). `BusClient.publishBatch(messages, { ack })` and
`BusRequestError.code` / `.details` are new.

Realtime: not done. `/api/stream` still polls `lastSeq` once a second. Driving it from
`bq.on("commit")` is easy, but every claim, renewal and ack is a commit too, so it would need a
"did `messages` change" check per event to be worth anything, and the dashboard reads the same
number either way.

Changes outside the bus. Importing `embedded.ts` for types put bql.sh's server modules under the
bus's `tsconfig`, which has the DOM lib; four spots disagreed with it and now cast through
`ConstructorParameters<typeof Response>[0]` (`http/handler.ts`, `server/workers/pool.ts`), `…<typeof
Headers>[0]` (`server/errors.ts`) and `never` for `KeyUsage[]` (`server/auth.ts`). No behaviour
change; `packages/db` typechecks as before.

Tests. `tests/preload.ts` (wired by `packages/bus/bunfig.toml`) reads `BUS_STORAGE=bql` and
replaces how `new BusStore(path)` turns a path into storage, via `setStorageFactory`: one engine
for the run, one database per `:memory:` store, one per file path so a reopen finds its data.
`bun run test:bql` runs it. Five tests were about the file itself (WAL truncation, `backup`, a
pre-versioning database written with `bun:sqlite`, a follower's file read from another process)
and now open `fileStorage(path)` explicitly, so they run on the file under both settings; the
"newer build" test writes its stray version through `raw()` and runs on both. New
`tests/storage.test.ts`: `fsync` publishes answer the committed txid (one txid per batch),
`replica` / `quorum` with no replica are `NO_REPLICAS` with the log and txid unchanged, an unknown
level is 400, the file backend answers 400 for `replica`, Tier 1 on bql commits the handler's row
with its ack and rolls both back on a throw, a publish during a snapshot waits it out, and a
synchronous route refused with `TX_BUSY` behind an interactive transaction runs again once it ends.

for what replication buys is the decision to make before step 6 flips the default. Batching (one
`publishBatch` is one record) is the lever for publish-heavy producers.

### Write-path profile

Where one publish goes on the bql backend, and what came off it. Measured in process, one
publish at a time, 4000 publishes per run after 500 to warm up, by wrapping `Tenant.write`,
`TxnRecorder.poll`, `TxnLog.append` / `appendEncoded` / `flush`, `Bun.zstdCompressSync`,
`Bun.hash.xxHash3`, `Database.exec` / `walCheckpoint` and the `fs` sync calls from a scratch script
(no instrumentation in the tree), plus `bun --cpu-prof-md` for anything the wrappers missed. Three
runs per side, before and after alternating, medians. Load was 7 to 10 on an 18-core machine, so
read the fsync lines as ±10 µs; the CPU lines repeated within about 1 µs.

| phase, µs per publish | `local` before | `local` after | `fsync` before | `fsync` after |
|---|---|---|---|---|
| `BEGIN IMMEDIATE` | 2.5 | 2.3 | 2.9 | 2.8 |
| statements, guard, `markStatement`, bookkeeping (the remainder) | 4 | 4 | 12 | 12 |
| `COMMIT` (SQLite writes the WAL frames, WAL hook) | 16.9 | 16.4 | 18.8 | 18.7 |

At `local` the encode and log write run in P5's microtask after `sync.write` returns, but this
loop pays them before the next publish either way. For comparison the file backend's whole
publish is 23 to 25 µs at `synchronous=NORMAL`, 18.7 of it `COMMIT`, and 42 µs at `FULL`, where
`COMMIT` includes the one WAL fsync.

Checked and not waste:

- **The guard.** `guarded` sets two fields per `sync.write`, and the driver asks the guard only at
  compile time and on a cache hit for a statement with a guarded action. `sync.write` against
  `tenant.write` with the same callback: 21.9 against 21.6 µs and 23.9 against 22.4 µs in two
  runs, which is noise.
- **`markStatement`, the commit listeners, `#savePosition`, `#wake`, realtime.** Under 0.1% of
  samples each in the CPU profile. Nothing subscribes to `bus`, so the capture hooks are not
  installed.
- **Commits per operation.** One `Tenant.write` per publish, per ack and per claim, in process and
  over HTTP (counted by wrapping `Tenant.write` behind a real server). A claim of 100 makes 102
  `sync.read` calls after its write (`subscriptionRow`, one `message()` per delivery); a
  `sync.read` point query is 0.84 µs against 0.67 µs straight on a connection, so that is under
  20 µs per claim of 100 and not worth moving into the write.
- **A small record skipping compression.** There is no such thing here: every record carries at
  least one full page and compresses 3x or better. `[durability] compress = false` is the switch,
  and it trades 4x the log for the zstd line.
- **fsync order and `fdatasync` for the log.** Swapping the order (WAL first) and `fdatasync`
  instead of `fsync` on the segment were each run three times against the current code: all
  within noise. On this disk two files cost about twice one file whichever way they are synced,
  and two `fs.fsync` calls in parallel on the thread pool were no faster than in a row.

What changed:

- **zstd level 1 for records** (`RECORD_ZSTD_LEVEL` in `packages/db/src/wal/record.ts`). On the
  bus's 18 KB, five-page publish body: 17 µs against 25 µs, ratio 3.48x against 3.49x. With 300
  words of text in each body: 25 against 33 µs, ratio 2.64x against 2.68x. `docs/performance.md`
  §6 rejected this for 1 µs on a one-page body and called it a format decision; it is neither on
  bigger records, and `decode` reads any level, so existing logs, replicas and buckets are
  unaffected. Snapshot shipping and the replica stream keep level 3.
- **The tailer reads frames in runs** (`packages/db/src/wal/tailer.ts`). It was one `readSync` per
  frame. Now a run starts at the previous poll's length plus one and doubles, up to 256 KiB, and
  each frame is still verified on its own. It cannot just read to the end of the file: after a
  checkpoint SQLite reuses the WAL from frame 1 and the file keeps its length, so a first try
  that read to EOF pulled up to 256 KiB of stale frames per poll and was slower than before. New
  test in `test/wal/tailer.test.ts`: a 200-page commit spanning several runs, then a RESTART and
  a one-page commit sitting in front of the big one's stale frames.
- **Schema version 11 drops `deliveries_ready`.** `deliveries_ready_priority` has the same three
  leading columns, and every status change rewrote one page per index holding `status`. An ack
  went from 6.1 to 5.1 pages per record.
- **`messages.id` and `deliveries.id` are UUIDv7** (`rowId()` in `store.ts`). Each insert lands
  near the right edge of the unique index instead of on a random leaf. The compressed publish
  record went from 5.5 KB to 3.8 KB, and the checkpoint has fewer distinct pages to copy. Other
  ids (subscriptions, blob handles, correlations) stay v4.

What remains is structural, and any binding that turns commits into a replicated log pays it:

- **A second barrier at `fsync`.** The log fsync (26 to 46 µs across runs) on top of the WAL's
  (19 to 22 µs). The file backend pays only the WAL's, inside `COMMIT`. The one way to drop it
  that I can see is to do at `fsync` what P5 does at `local`: answer after the WAL `fdatasync`
  and file the record afterwards, since the reconcile re-derives a lost record from the WAL. That
  would take the log fsync, zstd and the log write (about 55 µs) off the answer, but it changes
  what `ack: "fsync"` promises (log and WAL on disk) and the first tenant invariant, so it is
  not done here and needs a decision.
- **Capture: 16 µs of zstd, 9 to 10 of tailing and checksum folding, 5 to 9 of log write, 4 to 5
  of body copy and xxh3.** All per commit, so they divide by the batch size: `publishBatch` is one
  record.
- **Folding concurrent publishes.** The bus answers each publish with its own commit. A P2-style
  fold of concurrent publishes into one `sync.write` would share one capture and one pair of
  barriers between them, but folded publishes would share a txid, so it is not an
  identical-semantics change. `bench.ts` publishes one at a time and would not show it.

### Step 5 built

Both entry points work and share one module. `src/bus/node.ts` has `busNode({ bq, … })`: it
returns a `Mount` (`{ prefix: "/bus", fetch }`), and `start()` finds or creates database `bus`,
opens the store in this node's role and starts the timers. `src/cli/cluster.ts` (`serveBus`) loads
the keys, calls `busNode`, `bq.serve({ mount: [node.mount] })` and `start()`. `bql bus serve
--cluster --node n1 --peers n2=ws://…,n3=ws://… --port 4321` opens `Bql` from flags (plus
`--config bql.toml` for anything else) and calls it; `bql serve --bus` / `[bus] enabled = true`
opens `Bql` from the same inputs `startServer` would have used and calls it through a dynamic
import of `packages/bus/src/cli/cluster.ts`, the same way `bql bus …` already loads the bus CLI.
`pack:check` passes. `--bus` serves through the embedded API, so it is one worker and refuses
object storage.

The bus is not a second listener. `startServer` (and `bq.serve()`) take `mount: Mount[]`: a request
whose path is the prefix or under it goes to the mounted handler from the `fetch` fallback, after
bql.sh's own route table. That is what makes `BQL-Primary` right for the bus: it is
`runtime.primaryHttpFor("bus")` plus `/bus`, the node's one advertised address. `createServer`
gained `listen: false`, `basePath` and `primaryUrl`; the mounted handler strips the prefix, raises
the host's idle timeout for long polls (`server.timeout(req, 120)`), and the dashboard is served
with its asset links and API calls moved under the prefix (`window.__BUS_BASE`).

Startup. A clustered node waits until every configured peer is in the Raft membership, so
placement gives every node the same home for `bus`. The home node runs what `POST /v1/db` runs
(`promoter.assertMayCreate`, `registry.create`, `promoter.ensureLease`); the others wait for a
replica copy whose `schema_version` table has arrived. `bq.create` on its own skips the gate and the
lease claim; that is a bql.sh gap worth closing in `embedded.ts`, left alone here. A node
restarting after a failover still has `bus` marked primary in its own catalog until it is fenced,
so `start()` also waits until the node either holds the lease or is a replica.

Roles. `BusStore` takes `replica: true` (no migrations, writes refused), and has `becomePrimary()`
(migrate, accept writes, reload caches) and `becomeReplica()`. `reloadCaches()` drops schema
bindings, quotas, revocations and free space; a replica calls it every tick, because rows change
under it without passing through the store. A write on a replica, from the store's own check or
from bql.sh's `assertWritable` (a lease that lapsed between ticks), answers
`503 {"code":"NOT_PRIMARY","primary":…}` with `BQL-Primary`. The node reconciles on
`bq.on("role")` and on every tick against `bq.role("bus")`, one change at a time. The primary runs
the sweep (and the scheduler inside it) and blob collection; a replica runs neither. A claim long
poll checks the role on every pass and answers `NOT_PRIMARY` once the node is a replica. `/health`
reports `role`. Clustered nodes keep bodies in `blobs_data` (`--blob-store fs` is refused), set
`[sqlite] foreignKeys`, default `rf` to every node, and generate no keys: they refuse to start
without `BUS_SIGNING_KEY`/`keys.json` and `BUS_ADMIN_TOKEN`/`admin-token`.

`BusClient({ url: string | string[] })` (and `--url a,b,c`). It moves a request only when doing so
cannot repeat a write: `503 NOT_PRIMARY` follows `BQL-Primary` (or rotates when there is none), a
connection refused rotates, and a connection cut off mid-request or a timeout is retried only for a
GET or a publish whose every message has a `dedupeKey`. Anything else is thrown, `ACK_TIMEOUT`
included, and so is a redirect the CLI's transport refuses (the credential-forwarding test). With
more than one URL it also waits out `NO_REPLICAS`, which is refused before writing: after a
promotion the surviving replica takes a few ms to follow the new primary, and that window is what
made the first version of the cluster test flaky (measured: 0 ms on some runs, about 20 ms on
others; a publish landing in it threw). The loop is bounded by `failoverMs` (15 s) and 64 hops.

A bql.sh fix this needed. The drill failed about one run in eight with no promotion at all:
`/v1/cluster` showed the dead primary at `acked` 738 and both replicas at 737, the lease long
lapsed, and `decidePromotion` refusing with `BEHIND` for ever. A primary killed with a commit in
flight reports a txid no replica has, and the automatic failover compared against it.
`ClusterNode.#failover` now judges `BEHIND` among the reachable nodes only (`ackedAmong`). Nothing
past the best reachable copy was acknowledged at `replica` or `quorum`. An operator's
`promote` still compares against every node. Tested in `test/cluster/promotion.test.ts`, written up
in `docs/c2-promotion.md`. After it, 13 of 13 drills passed.

Also seen once, in the first drill run with bql.sh's own log at `warn`: after the promotion the
third node logged `ReplicaUnfollowed: bus was re-created … generation 282b… -> 0bbb…` and moved its
copy to `trash/`, i.e. it re-snapshotted from the new primary rather than continuing from its
position. The bus carried on (it looks the tenant up per call), but a full re-snapshot of `bus` on
every failover is a bql.sh question I have not chased.
